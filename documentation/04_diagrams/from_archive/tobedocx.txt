На основе предоставленных диаграмм будущего состояния (TO-BE) процесс автоматизированной обработки заявок на такси представляет собой целостную систему, построенную на взаимодействии нескольких ключевых модулей. Основной целью системы является автоматизация всего жизненного цикла заявки — от момента её создания сотрудником до формирования итогового файла для партнёра-исполнителя.
Центральным элементом системы является контекстная диаграмма A0, которая определяет её общие границы и взаимодействие с внешним окружением. В качестве входов система получает заявки от сотрудников, отправленные через специализированного Telegram-бота, а также запросы на отмену ранее поданных заявок, обозначенные как SOS-запросы. Выходами системы служат готовый Excel-файл, подготовленный для передачи партнёру, уведомления для сотрудников о статусе их заявок, а также подтверждения успешной отправки новых заявок. Управление процессом осуществляется через бизнес-правила валидации данных и регламент ручного согласования, который выполняет руководитель. Для реализации этих функций система использует механизмы в виде Telegram-бота с двумя интерфейсами — для сотрудника и для руководителя, а также серверную часть с базой данных.
Процесс детализируется на уровне декомпозиции A0 через три основных блока: A1, A2 и A3. Блок A1 отвечает за приём и нормализацию заявок. На этом этапе сотрудник взаимодействует с Telegram-ботом, заполняя форму с обязательными полями, включающими ФИО, адрес, телефон и дату с временем поездки. Система выполняет первичную валидацию данных, проверяя полноту информации и соответствие форматов. Для адресов применяется выборочная нормализация через внешний API геокодера, при этом сотрудник имеет возможность подтвердить нормализованный вариант или оставить исходный. После этого проверенная и, при необходимости, нормализованная заявка автоматически сохраняется в специальную мини-таблицу, которая служит буфером для последующего согласования.
Блок A2 осуществляет управление мини-таблицей и процесс согласования. Руководитель через веб-интерфейс просматривает заявки, которые автоматически сортируются по дате и времени. Система визуально выделяет потенциальные ошибки, например, подсвечивая проблемные строки. Руководитель обладает функционалом для прямого редактирования данных в таблице, включая использование выпадающего меню для повторной нормализации адресов. На основе проверки руководитель принимает решение по каждой заявке: одобрить её, отклонить или запросить у сотрудника исправления через систему уведомлений. Одобренные заявки направляются на дальнейшую обработку, а по команде руководителя выполняется операция полного слияния содержимого мини-таблицы с основной базой данных, после чего мини-таблица очищается.
Блок A3 занимается формированием итоговых данных для передачи партнёру. На этом этапе система накапливает согласованные заявки из основной базы данных и фильтрует их согласно определению рабочего дня, который установлен с 6:00 текущего дня до 5:59 следующего дня. Затем автоматически генерируется Excel-файл строго определённого формата, содержащий колонки с номером заявки, датой и временем, ФИО клиента, адресом и телефоном. Руководитель через свой интерфейс может просмотреть сформированный файл и скачать его. В случае возникновения ошибок при генерации Excel-файла система переходит в режим обработки сбоев, выполняя аварийную выгрузку данных в текстовом формате и уведомляя администратора о возникшей проблеме для её оперативного устранения.
Важным сервисом, обеспечивающим надёжность системы, является процесс резервного копирования. Каждые два часа автоматически создаётся резервная копия всей базы данных, которая сохраняется на срок до 24 часов. Это позволяет минимизировать риски потери информации в случае технических сбоев.
Все процессы между блоками взаимосвязаны. Поток данных начинается с A1, где заявки подготавливаются и помещаются в мини-таблицу. Далее в A2 эти заявки проверяются, редактируются и, после одобрения, переносятся в основную БД. Финализация происходит в A3, где данные фильтруются, форматируются и предоставляются руководителю в виде готового отчёта. Обратная связь также предусмотрена: если в A2 выявляются ошибки, требующие исправления, в A1 направляется соответствующий запрос, и сотрудник получает уведомление через бота. Таким образом, система представляет собой замкнутый, автоматизированный контур управления заявками, значительно снижающий ручной труд и вероятность ошибок по сравнению с предыдущим, полностью ручным процессом.
Usecase
1. Актор: Сотрудник
Сотрудник является основным пользователем системы и может выполнять следующие действия:
•	Зарегистрироваться по приглашению: Первоначальная регистрация в системе с использованием пригласительной ссылки или кода. Этот вариант использования включает в себя функцию «Валидировать приглашение».
•	Подать заявку на такси: Основное действие по созданию новой заявки на служебный транспорт.
o	Для подачи заявки сотрудник должен «Подтвердить нормализованный адрес» (отношение расширения <<extend>>).
o	Процесс подачи заявки расширяется (<<extend>>) за счет функции «Нормализовать адрес», которая выполняется автоматически.
•	Отменить заявку: Возможность отменить ранее поданную заявку.
•	Установить период "Не беспокоить": Настройка уведомлений или статуса недоступности.
•	Редактировать профиль: Обновление своей личной информации в системе.

2. Актор: Руководитель
Руководитель обладает расширенными правами для управления заявками и персоналом:
•	Просмотреть заявки: Просмотр списка всех заявок, поданных сотрудниками.
•	Одобрить заявку: Подтверждение поданной сотрудником заявки.
•	Отклонить заявку: Отказ в подтверждении заявки.
o	При отклонении заявки руководитель может «Указать причину отклонения» (отношение расширения <<extend>>).
•	Редактировать заявку сотрудника: Внесение изменений в заявки, созданные сотрудниками. Этот процесс включает в себя проверку «Проверить права доступа».
•	Просмотреть журнал аудита: Просмотр логов действий в системе.
•	Просмотреть список сотрудников: Получение списка всех зарегистрированных сотрудников.
•	Сформировать итоговый файл: Создание сводного отчета по заявкам.
•	Скачать итоговый Excel-файл: Выгрузка сформированного отчета в формате Excel.
•	Загрузить исправленный Excel-файл: Загрузка в систему файла с корректировками.
•	Добавить сотрудника: Внесение нового сотрудника в систему.
•	Удалить сотрудника: Удаление сотрудника из системы.
•	Нормализовать адрес: Запуск процесса нормализации адреса вручную.
o	Этот процесс может быть выполнен «Повторно нормализовать адрес» (отношение расширения <<extend>>).
o	Он также расширяет (<<extend>>) возможность «Редактировать заявку сотрудника», то есть может быть частью этого процесса.
________________________________________
3. Актор: Администратор
Администратор отвечает за техническое обслуживание и мониторинг системы:
•	Просмотреть системные логи: Анализ логов работы приложения для выявления ошибок.
•	Просмотреть журнал аудита: Просмотр логов действий пользователей (аудит).
•	Обработать аварийную ситуацию: Действия по устранению сбоев и нештатных ситуаций в системе.
________________________________________
4. Актор: Внешний Геокодер
Это внешняя система, которая предоставляет услуги для основного приложения:
•	Нормализовать адрес: Единственная функция — преобразование введенного текстового адреса в стандартизированный, структурированный формат. Эта функция используется системой при подаче заявки сотрудником и при повторной нормализации руководителем.
Ключевые связи и зависимости
•	Включение (<<include>>): Обязательная связь, когда один вариант использования не может быть выполнен без другого (например, «Подать заявку» включает «Проверить формат данных»).
•	Расширение (<<extend>>): Опциональная связь, когда один вариант использования может быть добавлен к другому при определенных условиях (например, «Отклонить заявку» может быть расширен за счет «Указать причину отклонения»).
