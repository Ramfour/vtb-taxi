СЛАЙД 2: ВВЕДЕНИЕ

ВВЕДЕНИЕ

Актуальность проблемы:
• Ежедневная обработка 50+ заявок на корпоративный транспорт
• Ручная обработка занимает 2-3 часа рабочего времени
• 15% заявок содержат ошибки при ручной обработке
• Отсутствие централизованной системы учета

Цель работы: Автоматизация процесса обработки заявок на корпоративный транспорт

СЛАЙД 3: ПОСТАНОВКА ЗАДАЧИ

ПОСТАНОВКА ЗАДАЧИ

Требования к системе:
• Автоматизация процесса создания и согласования заявок
• Ролевое разделение доступа (сотрудник, руководитель, администратор)
• Массовая обработка заявок руководителем
• Автоматический экспорт данных для перевозчика
• RESTful API для интеграции с внешними компонентами

Ограничения:
• Веб-интерфейс для руководителей (основная часть работы)
• API для интеграции с дополнительными компонентами
• Единая база данных

Примечание: Система также включает Telegram-бот как отдельный компонент, интегрируемый через API

---

СЛАЙД 4: АНАЛИЗ СУЩЕСТВУЮЩИХ РЕШЕНИЙ

АНАЛИЗ СУЩЕСТВУЮЩИХ РЕШЕНИЙ

Текущий процесс:
1. Сотрудник → Email/телефон → Руководитель
2. Руководитель → Ручная обработка → Excel таблица
3. Координатор → Формирование CSV → Перевозчик

Проблемы текущего процесса:
• Отсутствие единой базы заявок
• Дублирование информации
• Сложность отслеживания статуса
• Человеческий фактор
• Временные затраты

СЛАЙД 5: ПРОЕКТИРОВАНИЕ АРХИТЕКТУРЫ

ПРОЕКТИРОВАНИЕ АРХИТЕКТУРЫ

Выбор архитектуры:
• Модульный монолит на Laravel
• Двухслойная обработка заявок
• RESTful API для интеграции
• Ролевая модель безопасности

Стек технологий:
• Backend: PHP 8.3, Laravel 11.x
• Frontend: Blade, Tailwind CSS, JavaScript
• Database: MySQL 8.4
• API: RESTful для интеграции с внешними компонентами
• Deployment: Docker, Nginx

Дополнительные компоненты системы:
• Telegram-бот (отдельный сервис на Python)
• Внешние API для геокодирования

СЛАЙД 6: СХЕМА БАЗЫ ДАННЫХ

СХЕМА БАЗЫ ДАННЫХ

Основные таблицы:
• users (id, name, email, role, password, created_at, updated_at)
• temp_requests (id, user_id, address, phone, datetime, status, created_at, updated_at)
• requests (id, user_id, address, phone, datetime, status, exported_at, created_at, updated_at)
• audit_log (id, user_id, action, details, ip_address, created_at)

Связи:
• users 1:N temp_requests
• temp_requests 1:1 requests
• users 1:N audit_log

СЛАЙД 7: БИЗНЕС-ЛОГИКА

БИЗНЕС-ЛОГИКА ОБРАБОТКИ ЗАЯВОК

Процесс обработки:
1. Создание заявки → temp_requests
2. Валидация данных и уведомление руководителя
3. Согласование руководителем (редактирование/утверждение/отклонение)
4. Перенос утвержденных заявок в requests
5. Формирование CSV для перевозчика
6. Отметка exported_at и очистка

Двухслойная архитектура:
• Буферный слой (temp_requests) - для согласования
• Финальный слой (requests) - для экспорта

РЕАЛИЗАЦИЯ ВЕБ-ИНТЕРФЕЙСА

Функциональность:

СЛАЙД 9: API ИНТЕГРАЦИЯ

API ИНТЕГРАЦИЯ С ВНЕШНИМИ КОМПОНЕНТАМИ

RESTful API эндпоинты:
• POST /api/requests - создание заявки
• GET /api/requests/{id} - получение статуса
• PUT /api/requests/{id} - обновление заявки
• DELETE /api/requests/{id} - отмена заявки

Аутентификация API:
• API токены для внешних сервисов
• Ролевая проверка доступа
• Логирование всех запросов

Интеграция с Telegram-ботом:
• Отдельный сервис на Python + aiogram
• Обмен данными через REST API
• Единая база данных
