# Архитектура: задумано в Архитектура.docx vs реализовано сейчас

Ниже сравнение “как планировалось” (по документу `_about/Архитектура.docx`) и “как получилось” в текущем проекте.

## Что совпало

- **Модульный монолит на Laravel**: ядро системы действительно реализовано на Laravel, бизнес-логика централизована в серверной части.
- **Два слоя заявок**: буфер (`temp_requests`) и финальный слой (`requests`) присутствуют.
- **Роли и права**: разграничение Employee/Manager/Admin есть; проверка прав выполняется на сервере.
- **Отчетность/выгрузка**: реализована выгрузка в файл (CSV).
- **MySQL как основное хранилище**: совпадает с планом.

## Что упростили/не реализовали (главные отличия)

1. **Telegram-бот как отдельный сервис**
   - В документе: отдельный сервис-адаптер (Python + aiogram), который общается с Laravel по REST API.
   - В реализации сейчас: **Telegram-бот отсутствует**, используется веб-интерфейс как основной клиент.

2. **Redis и асинхронные очереди**
   - В документе: Redis Queue + воркеры для фоновых задач (геокодирование, уведомления).
   - В реализации сейчас: **фоновые очереди Redis не являются обязательной частью продакшна**. В docker они есть как опция, но критический путь работает синхронно.

3. **Геокодирование (Яндекс.Карты)**
   - В документе: геокодирование адресов через API и сохранение нормализованного адреса/координат.
   - В реализации сейчас: поля `address_norm/lat/lon` в БД предусмотрены, но **интеграция с внешним геокодированием не доведена как обязательная часть** (можно добавить позже).

4. **Excel vs CSV**
   - В документе: итоговый Excel-файл.
   - В реализации сейчас: **CSV** (это проще для эксплуатации, меньше зависимостей на сервере).

5. **Набор инфраструктуры**
   - В документе: акцент на очередях/воркерах как части backend.
   - В реализации сейчас: добавлены практичные вещи под shared-хостинг:
     - разделение “PHP web” и “PHP CLI” (в продакшне важно запускать artisan через PHP 8.3),
     - cron для `schedule:run`,
     - команда авто-очистки данных по срокам хранения (`taxi:cleanup`).

## Почему так получилось (прагматично)

- Проект запускался на **shared-хостинге**, где важно минимизировать зависимости (Redis/воркеры/доп. сервисы).
- Главная цель — **быстро дать рабочий сервис** для подачи/согласования заявок и выгрузки, без развертывания дополнительной инфраструктуры.
- Архитектура оставлена расширяемой: в будущем можно добавлять Telegram-бота, очереди и геокодирование без полной переделки базы и доменной модели.
