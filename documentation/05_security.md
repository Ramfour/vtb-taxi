# Безопасность проекта

Этот документ описывает текущие меры безопасности в проекте корпоративного такси, а также практичные рекомендации для дальнейшего усиления.

## 1) Аутентификация (кто вы)

- Используется стандартная аутентификация Laravel (сессионная).
- Пароли хранятся только в виде хэша (bcrypt) за счет `casts(): ['password' => 'hashed']` в модели `User`.
- В продакшне важно, чтобы `APP_KEY` был задан (иначе ломаются cookies/сессии и возможны 419 ошибки).

Рекомендации:

- Включить базовые требования к паролю (минимальная длина, запрет слишком простых).
- Добавить ограничение числа попыток входа (rate limit / lockout) для защиты от перебора.

## 2) Авторизация (что вам разрешено)

- Доступ к разделам ограничен по ролям через middleware `EnsureUserHasRole` (алиас `role` в роутинге).
- Роли фиксированы enum-ом `UserRole`:
  - Employee = 1
  - Manager = 2
  - Admin = 3

Рекомендации:

- Для критичных операций (удаления, перенос в финальный слой, выгрузки) дополнительно проверять роль и/или подтверждение действия (например отдельный POST + CSRF).

## 3) Защита запросов (CSRF)

- Все формы в web-интерфейсе защищены CSRF-механизмом Laravel.
- Ошибка 419 обычно означает проблему с сессией/CSRF:
  - неверный домен/протокол (www vs без www),
  - неверные настройки cookies,
  - нет прав на директории сессий при `SESSION_DRIVER=file`.

Рекомендации:

- Держать `APP_URL` в соответствии с реальным доменом и HTTPS.
- Следить за тем, чтобы `SESSION_DOMAIN` соответствовал выбранной стратегии (один домен или домен+поддомены).

## 4) Сессии и cookies

- Сессии могут храниться в файлах (`SESSION_DRIVER=file`) — это самый простой режим для shared-хостинга.
- При HTTPS рекомендуется `SESSION_SECURE_COOKIE=true`, чтобы cookies передавались только по защищенному каналу.

Рекомендации:

- Следить за правами на `storage/framework/sessions`, `storage/framework/cache`, `storage/logs`.
- При необходимости уменьшить размер cookies/заголовков, если появляются ошибки типа “Request Header Or Cookie Too Large”.

## 5) TLS/SSL (защищенный канал)

- Для боевого домена используется сертификат (желательно Let’s Encrypt) на оба имени: `vtb-taxi.ru` и `www.vtb-taxi.ru`.
- Важно настроить редирект на единый канонический домен (с www или без), чтобы не было “двух версий” сайта.

Рекомендации:

- Включить автопродление SSL (или поставить напоминание за 10 дней до окончания).
- По возможности добавить HSTS (если хостинг/конфиг позволяет).

## 6) Логи и аудит (кто что сделал)

- Есть отдельная таблица `audit_logs`, запись идет через `AuditLogger`.
- Аудит пишется “best-effort” (ошибка аудита не ломает основной сценарий).

Рекомендации:

- Не логировать чувствительные данные (пароли, ключи, токены).
- Ограничить доступ к разделу аудита только администратору.

## 7) Персональные данные (PII)

Проект хранит персональные данные:

- ФИО, телефон, адрес подачи, время поездки.

Рекомендации:

- Ограничить доступ к данным по принципу минимальных привилегий (Employee видит только свои записи).
- Настроить политику хранения (retention) и авто-очистку, чтобы данные не копились “вечно”.
- Для выгрузок хранить только то, что нужно перевозчику.

## 8) Retention / авто-очистка данных

Есть команда `taxi:cleanup` и планировщик Laravel Scheduler (через cron `schedule:run`).

Типовая политика:

- `temp_requests` очищать через 7 дней,
- `requests` удалять через 5 дней после `exported_at` (после выгрузки CSV),
- `audit_logs` хранить 90 дней.

Это снижает риск накопления PII и уменьшает “поверхность атаки”.

## 9) Секреты и репозиторий

- `.env` не должен попадать в git.
- В репозиторий нельзя класть:
  - дампы БД с реальными данными,
  - приватные ключи SSL,
  - любые токены и пароли.

Рекомендации:

- Проверять `.gitignore` и историю коммитов перед публикацией.
- Менять пароли/ключи, если они случайно “утекли” в чат/лог/репозиторий.

## 10) Рекомендации “быстрого усиления” (минимум усилий)

- Rate limiting на логин и критичные POST-ручки.
- Security headers (если доступно): `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Content-Security-Policy` (хотя бы базовый).
- Двухфакторная аутентификация для Admin (если потребуется).
- Регулярные бэкапы БД (и проверка восстановления).
