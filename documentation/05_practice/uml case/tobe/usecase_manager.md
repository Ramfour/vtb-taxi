# Use Case: Руководитель (Manager)

Источник диаграммы: `usecase_manager.drawio`.

Диаграмма описывает сценарии работы руководителя: согласование заявок сотрудников и подготовка выгрузки для перевозчика.

## Актор

- **Руководитель (Manager)** — принимает решения по заявкам и формирует итоговую выгрузку.

## Сценарии (use cases) и что они означают

### 1) Войти в систему

**Связь с проектом (роуты):**

- `GET /login` → `login`
- `POST /login` → `login.store`

### 2) Просмотреть очередь заявок (Pending)

**Смысл:** открыть очередь заявок “на согласовании” (буфер).

**Связь с проектом (роуты):**

- `GET /manager/requests` → `manager.requests.index`

**Где хранится:** таблица `temp_requests` со статусом “ожидает” (Pending).

### 3) Одобрить / отклонить заявку / заявки

**Смысл:** принять решение по одной заявке или массово по нескольким:

- одобрить (Approved),
- отклонить (Rejected) с причиной/комментарием,
- при необходимости отредактировать поля заявки перед решением.

**Связь с проектом (роуты):**

- `PATCH /manager/requests/{tempRequest}/review` → `manager.requests.review`
- `POST /manager/requests/bulk-approve` → `manager.requests.bulk-approve`

### 4) Перенести одобренные в финальный слой (`requests`)

**Смысл:** после согласования руководитель “финализирует” одобренные заявки: переносит их из буфера `temp_requests` в финальную таблицу `requests`.

Это важно для разделения слоёв:

- `temp_requests` — очередь на согласовании (может меняться),
- `requests` — финальный набор данных, который выгружается в CSV.

**Связь с проектом (роуты):**

- `POST /manager/requests/finalize` → `manager.requests.finalize`

### 5) Скачать CSV (по диапазону дат)

**Смысл:** сформировать и скачать CSV-файл с подтверждёнными поездками.

**Связь с проектом (роуты):**

- `POST /manager/requests/export-csv` → `manager.requests.export-csv`

**Дополнительно:** при выгрузке строки в `requests` помечаются временем `exported_at` для политики хранения и последующей очистки.

### 6) Создать / удалить приглашение

**Смысл:** руководитель может создавать приглашения для регистрации сотрудников (и при необходимости удалять их).

**Связь с проектом (роуты):**

- `POST /manager/invitations` → `manager.invitations.store`
- `DELETE /manager/invitations/{invitation}` → `manager.invitations.destroy`

Также есть публичный сценарий “принять приглашение”:

- `GET /invite/{token}` → `invitation.accept.show`
- `POST /invite/{token}` → `invitation.accept.store`

## Что руководитель НЕ делает в рамках этой диаграммы

- Не управляет глобальными настройками системы.
- Не обязан иметь доступ к аудиту (это роль Admin).
