# AS-IS: UML Use Case (Руководитель)

Источник диаграммы: `руководитель.xml`.

Диаграмма отражает ранний процесс (AS-IS), в котором руководитель вручную проверял данные, редактировал и сообщал сотруднику результат.

## Актор

- **Руководитель** — проверяет заявки/правки, принимает решение, фиксирует изменения и отправляет сотруднику статус.

## Сценарии (use cases)

### 1) Просмотреть статус заявки

**Смысл:** понять, что сейчас с заявкой: новая, на проверке, подтверждена, отменена и т.п.

### 2) Редактировать заявку

**Смысл:** исправить/уточнить данные заявки, если это возможно без участия сотрудника.

### 3) Направить данные о статусе заявки

**Смысл:** отправить сотруднику результат рассмотрения (уведомление о статусе).

### 4) Логировать изменение

**Смысл:** фиксировать, какие изменения были внесены (идея будущего аудита).

## Поддерживающие функции

- **Валидация данных**: проверка корректности заявки.
- **Нормализация адресов (улица, номер дома)**: стандартный формат адреса.

В AS-IS эти функции показаны как обязательные подшаги (через include).

## Отличие от текущего проекта

В текущем продукте:

- руководитель работает в web-интерфейсе с очередью `temp_requests`,
- принимает решения (approve/reject) и может делать массовые операции,
- переносит одобренные заявки в `requests`,
- выгружает CSV,
- аудит реализован отдельной таблицей и интерфейсом.

То есть “направить данные о статусе заявки” стало обновлением статуса в БД + отображением результата в UI сотрудника (и потенциально уведомлениями при расширении).
