ГЛАВА 1. АНАЛИЗ ПРЕДМЕТНОЙ ОБЛАСТИ И ФОРМИРОВАНИЕ ТРЕБОВАНИЙ
(Здесь 80% материала берется из ваших лекций по интерфейсам, Стадия 1 и начало Стадии 2)
1.1. Технико-экономическая характеристика объекта (ПАО ВТБ, отдел ДКО)
•	Описание деятельности отдела (AS-IS).
•	Выявление «узких мест» ручного процесса (по тексту вашего документа).
1.2. Анализ пользователей системы (Стадия 1: Сбор информации)
•	1.2.1. Профили пользователей (Персоны): Описать Руководителя и Сотрудника по шаблону из лекции (демография, опыт, мотивация).
•	1.2.2. Анализ рабочей среды: Описать условия труда в колл-центре (шум, освещение, стационарный ПК) — это обоснование выбора Web + Telegram.
•	1.2.3. Анализ задач пользователей (Иерархия): Декомпозиция задачи «Заказ такси» на подзадачи (Заполнение формы -> Отправка -> Проверка статуса).
•	1.2.4. Сбор требований к интерфейсу: Формализация требований из документа («сократить время обработки заявки до 2 минут», «исключить потерю данных»).
1.3. Обоснование необходимости разработки и выбор концепции
•	Сравнение с аналогами (Яндекс.Бизнес, 1С). Обоснование гибридного подхода (Web + Telegram Bot).
•	Формирование целевого процесса (TO-BE).
1.4. Разработка сценариев взаимодействия (Use Cases) (Стадия 2: Разработка сценариев)
•	Это уже не "что делает", а "как будет делать в новой системе".
•	1.4.1. Сценарий «Сотрудник подает заявку через Telegram» (Основной и альтернативный потоки, таблица «Действие — Ответ»).
•	1.4.2. Сценарий «Руководитель обрабатывает буфер заявок в Web».
•	Диаграмма вариантов использования (UML Use Case Diagram).
1.5. Техническое задание (краткое) / Спецификация требований

ГЛАВА 2. ПРОЕКТИРОВАНИЕ АРХИТЕКТУРЫ И БАЗЫ ДАННЫХ
(Здесь начинается «жесткая» инженерия. Интерфейс пока не рисуем, думаем о том, как это будет работать под капотом)
2.1. Выбор и обоснование архитектурного решения
•	2.1.1. Архитектурный стиль: Обоснование выбора Микросервисного подхода (или Модульного монолита) для обеспечения отказоустойчивости бота и веба.
•	2.1.2. Диаграмма компонентов системы: Схема: Telegram Client <-> Bot Service (Python) <-> Backend API (Laravel) <-> Database (MySQL).
2.2. Проектирование базы данных
•	2.2.1. Логическая модель (ER-диаграмма): Сущности User, Request, Buffer, AuditLog. Связи.
•	2.2.2. Физическая модель данных: Обоснование типов полей (почему BIGINT для Telegram ID, VARBINARY для шифрования ФИО). Описание ограничений целостности.
2.3. Определение объектов и операций интерфейса (Стадия 2.3)
•	Это мостик между БД и интерфейсом.
•	Таблица «Объект — Операции — Тип доступа». Например: Объект Заявка. Операции: Создать (Сотрудник), Одобрить (Руководитель), Просмотреть список (Руководитель).

3.2. Проектирование пользовательского интерфейса (Стадия 2.4-2.6)

ГЛАВА 4. ТЕСТИРОВАНИЕ И ОЦЕНКА КАЧЕСТВА ИНТЕРФЕЙСА
(Эта глава полностью строится на Стадии 4 из лекций)
4.1. Функциональное тестирование
•	Проверка API через Postman.
•	Тестирование сценариев (проверка того, что кнопка «Сформировать Excel» действительно выгружает файл).
4.2. Подтверждение качества пользовательского интерфейса (Usability Testing)
•	4.2.1. Методика и условия тестирования: Выборка пользователей (5 человек из отдела), лабораторное/удаленное тестирование.
•	4.2.2. Метрики удобства: Время выполнения задачи, количество ошибок, оценка по шкале SUS (System Usability Scale).
•	4.2.3. Анализ результатов: Сравнение с ручным процессом (AS-IS). Подтверждение снижения времени обработки с 25 мин до 2 мин.
4.3. Оценка экономической эффективности
•	Расчет экономии времени руководителя (по данным из вашего документа).
