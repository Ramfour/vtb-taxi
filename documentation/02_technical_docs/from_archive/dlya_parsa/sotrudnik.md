# AS-IS: UML Use Case (Сотрудник)

Источник диаграммы: `сотрудник.xml`.

Диаграмма показывает, какие действия сотрудник выполняет в “старом/раннем” процессе (AS-IS), где взаимодействие было задумано через отправку сообщений и получение уведомлений.

## Актор

- **Сотрудник** — инициирует изменения по заявке и получает обратную связь о статусе.

## Сценарии (use cases)

### 1) Отправить сообщение

**Смысл:** базовая операция коммуникации — сотрудник “передает” данные заявки/правок.

Эта операция используется как фундамент для других сценариев (заявка, корректировка, отмена).

### 2) Отправить корректировку

**Смысл:** сообщить изменения по уже созданной заявке (например, корректировка адреса/времени).

### 3) Отменить заявку

**Смысл:** запросить отмену поездки/заявки.

### 4) Сменить адрес/время

**Смысл:** частный случай корректировки, когда меняются ключевые поля поездки.

### 5) Получить уведомление о статусе заявки

**Смысл:** получить итог от руководителя — одобрено/отклонено/нужно уточнение.

## Поддерживающие функции

На диаграмме присутствуют блоки, отражающие “обработку” данных:

- **Валидация данных**: проверка корректности введенной информации.
- **Нормализация адресов (улица, номер дома)**: приведение адреса к стандартизированному виду.

Смысл в AS-IS: эти шаги могли выполняться как обязательные части обработки заявки (через include).

## Отличие от текущего проекта

В текущем продукте сотрудник работает через веб-портал:

- создание заявки → `temp_requests`,
- просмотр и отмена → UI в кабинете сотрудника,
- статус виден в интерфейсе.

То есть “отправить сообщение” в AS-IS фактически заменилось формой в UI + сохранением в БД.
