Общее описание архитектурного стиля

Архитектура системы представляет собой модульный монолит на базе фреймворка Laravel. Основная бизнес-логика централизована внутри одного серверного приложения, которое обрабатывает пользовательские запросы, взаимодействует с базой данных MySQL, формирует веб-интерфейс и выполняет регламентные задачи по расписанию. Основной способ работы с системой — веб-интерфейс, доступный через браузер с компьютера или мобильного устройства.

Система построена по классической для Laravel схеме: клиент обращается к приложению по HTTPS, запрос проходит через маршрутизацию, middleware и контроллеры, далее передаётся в сервисный слой, где выполняется прикладная логика, после чего данные либо сохраняются в базе, либо возвращаются пользователю в виде HTML-страницы, таблицы или файла выгрузки. Такой подход обеспечивает целостность логики, упрощает сопровождение проекта и делает систему удобной для развёртывания на стандартном хостинге.

Логически архитектуру можно разделить на три уровня:

клиентский слой;
серверный слой;
слой данных и инфраструктуры.
Клиентский слой

Клиентский слой реализован в виде серверно-рендеримого веб-интерфейса. Пользователь работает с системой через браузер, а страницы формируются средствами Laravel и Blade. Интерфейс включает страницы для сотрудников, руководителей и администраторов, а также вспомогательные разделы, связанные с управлением заявками, просмотром истории, аудитом и работой с пользователями.

Пользовательский интерфейс строится на шаблонах Blade, что позволяет объединить представление и серверную логику в рамках одного приложения. Для оформления используются Tailwind CSS и дополнительные стили проекта. Для отдельных интерактивных элементов применяется лёгкий JavaScript, не превращающий приложение в полноценную SPA-систему. Это означает, что основная логика взаимодействия остаётся серверной: действия пользователя приводят к отправке запроса на сервер, после чего сервер возвращает уже готовый результат.

В интерфейсе используются формы, таблицы, статусы, элементы навигации, модальные окна и другие стандартные компоненты прикладной корпоративной системы. Все формы работают с CSRF-защитой, а состояние авторизации поддерживается через сессии Laravel.

Серверный слой

Серверный слой представляет собой ядро системы на Laravel. Он включает маршрутизацию, промежуточные обработчики запросов, контроллеры, сервисный слой, модели Eloquent и шаблоны представлений.

Обработка пользовательского запроса происходит поэтапно. Сначала запрос поступает в маршруты Laravel. Затем он проходит через middleware, где выполняются проверки сессии, аутентификации, CSRF-защиты и прав доступа. После этого запрос передаётся в контроллер, который не содержит в себе всю бизнес-логику, а делегирует её специализированным сервисам. Такой подход делает контроллеры компактными, а прикладное поведение системы — более структурированным и удобным для сопровождения.

Сервисный слой играет ключевую роль в архитектуре. Именно в нём сосредоточены основные бизнес-процессы: обработка заявок, перенос данных между слоями хранения, фиксация изменений, подготовка выгрузок и вызов регламентных операций. Контроллеры выступают как точка входа, а сервисы — как место, где реализуются правила предметной области.

Для работы с данными используются модели Eloquent. Они представляют таблицы базы данных в виде объектной модели и обеспечивают чтение, запись, обновление и удаление данных. Благодаря этому серверная часть сочетает удобство разработки с достаточно строгой структурой доступа к данным.

Аутентификация и контроль доступа

В системе предусмотрено разграничение прав доступа между основными ролями пользователей: сотрудником, руководителем и администратором. Контроль доступа реализован на стороне сервера и не зависит только от элементов интерфейса. Даже если пользователь попытается обратиться к недоступному разделу напрямую, окончательная проверка прав всё равно выполняется в backend-слое.

Для этого используются стандартные механизмы Laravel: аутентификация, middleware и проверки ролей. Такой подход особенно важен для операций согласования заявок, управления пользователями, просмотра аудита и доступа к административным разделам.

Работа с заявками

Центральной частью прикладной логики системы является обработка заявок. Архитектура предусматривает двухэтапную модель хранения: сначала заявки попадают во временный слой, после чего, в зависимости от результата обработки, могут быть перенесены в основной слой хранения.

Такой подход позволяет разделить необработанные и финальные данные. Временный слой используется как буфер, в котором заявки находятся до момента рассмотрения. Это помогает организовать управляемый жизненный цикл заявки, отделить промежуточные записи от основной истории и обеспечить более понятную схему работы для руководителей и сотрудников.

После обработки данные переносятся в основное хранилище, где уже составляют финальную историю заявок. Такая организация упрощает контроль статусов, аудит действий и подготовку итоговых выборок для отчётности.

Слой данных

Основным хранилищем данных выступает MySQL. В базе данных размещаются сведения о пользователях, ролях, заявках, временных заявках, приглашениях, адресах, журналах аудита и других сущностях, необходимых для работы системы.

Выбор MySQL обусловлен тем, что прикладная область хорошо описывается реляционной моделью: между сущностями существуют понятные связи, данные требуют согласованности, а значительная часть операций связана с выборками, фильтрацией, обновлением статусов и фиксацией истории изменений. Использование реляционной базы данных обеспечивает надёжное хранение информации и хорошо сочетается с архитектурой Laravel.

Работа с базой данных ведётся через Eloquent ORM и систему миграций. Это позволяет хранить структуру БД в коде, поддерживать повторяемость развертывания и упрощать развитие проекта.

Файловое хранилище

Помимо базы данных, важную роль играет файловое хранилище приложения — каталог storage/. В нём располагаются runtime-данные системы: сессии, логи, временные и экспортируемые файлы.

Наличие корректно настроенного storage/ принципиально важно для стабильной работы системы. Через него обеспечивается хранение пользовательских сессий, запись журналов работы приложения и формирование файлов выгрузки. Если права доступа к этой директории настроены неправильно, возможны проблемы с авторизацией, логированием и экспортом данных.

Таким образом, storage/ является не просто техническим элементом Laravel, а полноценной частью архитектуры, обеспечивающей работу прикладного сервиса в продакшене.

Серверная инфраструктура

Система размещается на стандартной серверной инфраструктуре без обязательного использования контейнеризации в продакшене. Пользовательский запрос проходит типичную цепочку: доменное имя через DNS указывает на сервер, защищённое соединение устанавливается по HTTPS с использованием SSL/TLS, веб-сервер принимает запрос и передаёт его в PHP runtime, после чего выполнение продолжается в точке входа Laravel — public/index.php.

Веб-сервером может выступать nginx или Apache. На стороне PHP приложение рассчитано на работу с PHP 8.3, причём важно, чтобы и веб-обработка, и запуск CLI-команд происходили на совместимой версии PHP. Это особенно важно для корректной работы команд Laravel и зависимостей проекта.

Корневой директорией сайта должен быть каталог public/, поскольку именно он предназначен для безопасной публикации веб-части Laravel-приложения. База данных MySQL подключается как отдельный инфраструктурный компонент, а доступ к ней осуществляется только через backend-приложение.

Защищённое соединение обеспечивается SSL-сертификатом. Это необходимо не только для безопасности передачи данных, но и для корректной работы авторизации, пользовательских сессий и общего доверия к системе.

Планировщик задач

Для выполнения регламентных операций в системе используется связка внешнего cron и встроенного Laravel Scheduler. Внешний cron по расписанию запускает команду artisan schedule:run, а уже внутри Laravel выполняются конкретные задачи обслуживания.

Такой механизм позволяет автоматизировать периодические процессы без необходимости разворачивать отдельные фоновые сервисы. Регламентные задачи могут быть связаны с очисткой данных, обслуживанием временных сущностей, техническими процедурами сопровождения и другими внутренними функциями системы.

Подобная схема хорошо подходит для размещения на обычном хостинге, так как не требует сложной инфраструктуры и при этом обеспечивает достаточную гибкость для автоматизации повторяющихся операций.

Отчётность и выгрузки

Система поддерживает формирование выгрузок по данным заявок. Выгрузка используется как прикладной механизм подготовки информации для дальнейшей работы вне системы. Архитектурно эта возможность реализована как часть серверного приложения: данные извлекаются из базы, обрабатываются на стороне backend и сохраняются в файл, который затем может быть передан пользователю.

Подсистема выгрузок встроена в общую прикладную логику и не требует отдельного внешнего сервиса. Это соответствует общему архитектурному принципу проекта, где основной функционал сосредоточен внутри одного Laravel-приложения.

Технологический стек

Текущий стек проекта включает:

Laravel как основной backend-фреймворк;
PHP 8.3 как среду исполнения;
MySQL как основную реляционную базу данных;
Blade как шаблонизатор пользовательского интерфейса;
Tailwind CSS для стилизации;
Vite и laravel-vite-plugin для сборки фронтенд-ассетов;
nginx или Apache как веб-сервер;
cron и Laravel Scheduler для выполнения задач по расписанию;
storage/ как файловое хранилище runtime-данных.

Такой стек образует цельную и практичную архитектуру, ориентированную на надёжную работу, понятную поддержку и относительную простоту развёртывания.

Итоговое резюме

Архитектура системы построена как модульный монолит на Laravel с серверным веб-интерфейсом, централизованной бизнес-логикой и реляционным хранилищем данных на MySQL. Пользователь работает через браузер, серверная часть обрабатывает запросы, контролирует права доступа, управляет жизненным циклом заявок, формирует выгрузки и выполняет регламентные задачи через встроенный планировщик.

Система не опирается на сложную распределённую инфраструктуру, а использует более практичную и устойчивую схему: веб-сервер, PHP, MySQL, файловое хранилище, HTTPS и cron. Это делает решение удобным для сопровождения, развёртывания и дальнейшего развития.

В целом архитектура отражает прикладной характер системы: она ориентирована на надёжную обработку заявок, прозрачную серверную логику, разграничение прав, хранение истории и удобную эксплуатацию в реальных условиях корпоративного использования.
