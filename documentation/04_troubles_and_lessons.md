# Трудности, причины и как решали

Ниже список реальных проблем, с которыми столкнулись при доведении проекта до продакшна, и почему они возникли.

## 1) 419 Page Expired (Laravel)

**Симптом:** после логина/POST-запросов Laravel возвращал 419.

**Причины (типовые):**

- не задан `APP_KEY` на сервере,
- несоответствие домена/протокола: заход на `www` при `SESSION_DOMAIN` для “без www” (или наоборот),
- неверные настройки `SESSION_SECURE_COOKIE`, `APP_URL`,
- недоступность/права на `storage/framework/sessions` при `SESSION_DRIVER=file`.

**Как исправляли:**

- сгенерировали и задали `APP_KEY`,
- привели домены/HTTPS к единым настройкам,
- проверили права на `storage/` и очистили кеши artisan-командами.

## 2) PHP CLI не той версии (8.2 вместо 8.3)

**Симптом:** `php artisan ...` падал на `composer/platform_check.php` (проект требует `php ^8.3`).

**Причина:** на хостинге “PHP версии 8.3” был выставлен для web (FastCGI), но `php` в shell указывал на 8.2.

**Решение:** запускать artisan через явный путь:

- `/opt/php/8.3/bin/php artisan ...`

## 3) Ошибки вида “Unknown column …” / “status = 0 is not valid backing value”

**Симптом:** 500 ошибки при создании/согласовании/переносе заявок, в логах:

- `Unknown column reviewed_at/approved_at/lat/...`
- `0 is not a valid backing value for enum App\Enums\RequestStatus`

**Причины:**

- схема БД не совпала с кодом (часть таблиц/полей создавалась вручную/из SQL, часть — миграциями),
- значения `status` не соответствовали enum-ам (в проекте `Pending=1`, `Approved=2`, …).

**Решение:**

- выровняли схему миграциями и/или `ALTER TABLE`,
- поправили данные/дефолты, чтобы статусы были 1..5.

## 4) Права на `storage/` и экспорты

**Симптом:** ошибки при записи в `storage/…` (сессии/логи/экспорт CSV).

**Причина:** в shared-хостинге/контейнере директории могут быть без прав на запись для пользователя webserver.

**Решение:** выставили права на запись для нужных директорий (`storage/framework/*`, `storage/logs`) и добавили обработку ошибок при сохранении CSV, чтобы скачивание работало даже если сохранение на диск недоступно.

## 5) SSL “не защищено” при одном из доменов

**Симптом:** `www` защищен, а домен без `www` — нет.

**Причина:** сертификат Let’s Encrypt был выпущен только на один SAN (например только `www…`), либо требовалось время на применение.

**Решение:** выпустили сертификат на оба домена (`vtb-taxi.ru` и `www.vtb-taxi.ru`) и привязали к сайту, после чего подождали распространения изменений.

## 6) UI/мобильная адаптация и “вылазки”

**Симптом:** элементы вылезали вправо, слипались, таблицы были неудобны на мобильных.

**Причина:** плотная табличная раскладка плохо ложится на узкие экраны; любые “умные” мобильные карточки легко ломают интерактивные элементы (чекбоксы/кнопки).

**Решение:** сделали более устойчивые стили, ограничили ширины, добавили переносы и прокрутку, проверяли на конкретных разрешениях.

## 7) AJAX-переходы без перезагрузки

**Симптом:** при попытке “без перезагрузки” ломались клики/валидация и появлялись регрессии.

**Причина:** форма/редиректы в Laravel по умолчанию предполагают полноценный POST-redirect-GET; частичный AJAX требует аккуратной синхронизации состояния, ошибок и якорей, плюс нужна защита от двойных сабмитов.

**Решение:** для критичных действий сохранили надежный server-side поток (PRG), а улучшения UX делали точечно там, где это не ломает поток.

## Что стоит помнить в дальнейшем

- Любое изменение схемы БД: сначала миграции, потом проверка на проде (`migrate --force`).
- На хостингах всегда проверять: версия PHP для web и для shell (artisan).
- SSL: лучше сразу выпускать сертификат на `domain` + `www`, и настраивать редирект на один “канонический” адрес.
- Для очистки данных нужен cron, иначе команды будут работать только “вручную”.
