 
                  База данных системы автоматизации заказа корпоративного такси                   1. Общие сведения           База данных разработана для хранения информации о пользователях, приглашениях, заявках на такси и журнала аудита. Она спроектирована с учётом требований безопасности (шифрование персональных данных) и специфики бизнес-процессов отдела ДКО ПАО ВТБ в г. Новосибирске.                  СУБД    : MySQL 8.0 (совместимо с      MariaDB      10.3+)                  Кодировка    : utf8mb4_unicode_ci – полная поддержка      Unicode     , корректная сортировка кириллицы.                  Движок    :      InnoDB      – поддержка транзакций, внешних ключей, каскадного удаления.           База данных состоит из пяти таблиц:               users      – пользователи системы (сотрудники и руководители).               invitations      – одноразовые приглашения для регистрации сотрудников.               temp_requests      – буфер заявок, ожидающих рассмотрения руководителем.               requests      – архив одобренных заявок, готовых к выгрузке.               audit_logs      – журнал аудита действий пользователей.                               2. Логика шифрования персональных данных           Все поля, помеченные как «шифруются», хранятся в базе данных в зашифрованном виде. Шифрование и дешифрование выполняется на уровне приложения      Laravel      с использованием      кастов           encrypted      (или кастомных      кастов     ).                   Почему тип данных TEXT?           Зашифрованная строка значительно длиннее исходной, особенно при использовании алгоритмов с вектором инициализации. Тип TEXT (до 65 535 байт) даёт необходимый запас.                   Какие поля шифруются:                                                    Таблица                        Поля                              users                                full_name        , phone,         default_address                               temp_requests                                full_name        , phone,         address_raw        ,         address_norm                               requests                                full_name        , phone,         address_raw        ,         address_norm                       Важно:              Администратор базы данных (имеющий доступ к      phpMyAdmin     )         видит только зашифрованные данные    .              Руководители в веб-интерфейсе видят расшифрованные данные благодаря работе      Laravel     .              Ключ шифрования хранится в      файле .     env       приложения и         не попадает     в базу данных.                               4. Связи между таблицами (ER-диаграмма словами)                  Приглашения     создаются         руководителем     (     invitations.created     _by → users.id).                     Пользователь     может быть создан по         приглашению            (         users.invitation        _id         → invitations.id).                     Сотрудник            подаёт                буферные                  заявки        (        temp_requests.user_id         → users.id).                     Руководитель            обрабатывает                буферные                  заявки        (        temp_        requests.manager        _id         → users.id).                  Одобренные заявки     переносятся в         архив     с указанием         руководителя     (requests.user_id,      requests.approved     _by → users.id).                  Аудит     ссылается на         пользователя    , но при удалении пользователя записи сохраняются (     audit_logs.user_id      → users.id ON DELETE SET NULL).                               5. Сценарии работы с данными                   5.1. Создание приглашения и регистрация сотрудника              Руководитель в веб-интерфейсе вводит табельный номер нового сотрудника и нажимает «Создать приглашение».              В таблице      invitations      создаётся запись с уникальным      token      и      created_by      =      id      руководителя.              Система формирует URL вида https://taxi.vtb.local/register/{token}.              Сотрудник переходит по ссылке, вводит недостающие данные (ФИО, телефон, адрес по умолчанию, пароль). При желании подключает      Telegram     -бота (виджет возвращает      telegram_id     ).              Создаётся запись в      users      с      invitation_id      =      id      использованного приглашения.              Приглашение помечается как      is_used      = 1,      used_at      =      NOW(     ).                   5.2. Подача заявки сотрудником               Сотрудник через веб или бота заполняет форму: адрес, дата/время, телефон (подставляется из профиля).              Данные проходят первичную валидацию.              Создаётся запись в      temp_requests      со статусом      pending     .              В очередь      Redis      отправляется задача на нормализацию адреса (     address_norm     ).              Руководитель получает уведомление о новой заявке.                   5.3. Обработка заявки руководителем              Руководитель открывает веб-интерфейс, видит список заявок из      temp_requests      со статусом      pending     .              Для каждой заявки может:                  Одобрить    : статус меняется на      approved     , заполняется      manager_id     .                  Отклонить    : статус меняется на      rejected     , заполняются      manager_id      и      rejection_reason     .              При изменении статуса отправляется уведомление сотруднику через      Telegram     -бота.                   5.4. Перенос одобренных заявок в архив              В конце рабочего дня (или по команде) руководитель нажимает «Сформировать итоговый список».              В         транзакции     выполняются два запроса:                  sql                  INSERT INTO requests (        user_id        ,         full_name        , phone,         address_raw        ,         address_norm        ,         date_time        ,         approved_by        )                 SELECT         user_id        ,         full_name        , phone,         address_raw        ,         address_norm        ,         date_time        ,         manager_id                  FROM         temp_requests                  WHERE status = 'approved' AND         DATE(         date_time        ) =         CURDATE(        );                           DELETE FROM         temp_requests                  WHERE status = 'approved' AND         DATE(         date_time        ) =         CURDATE(        );              Транзакция гарантирует, что данные не потеряются и не задвоятся при сбое.                   5.5. Генерация Excel-файла              Руководитель нажимает «Экспорт в Excel».              Сервис отчётов выбирает все записи из      requests      за текущий день (или по заданному фильтру).              Данные расшифровываются на уровне приложения.              Библиотека      PhpSpreadsheet      формирует файл в формате, требуемом Яндекс Go.              Файл отдаётся на скачивание.                   5.6. Аудит действий           При каждом значимом действии (создание/изменение/удаление заявки, вход в систему, создание приглашения) в таблицу      audit_logs      добавляется запись с описанием, IP-адресом и временем. Это позволяет отследить, кто и когда вносил изменения.                                6. Резюме           Спроектированная база данных обеспечивает:              Надёжное хранение пользователей и заявок с соблюдением требований безопасности.              Контролируемую регистрацию сотрудников через механизм одноразовых приглашений.              Чёткое разделение временных (буфер) и архивных данных заявок.              Полноценный аудит действий для расследования инцидентов.              Возможность быстрого формирования отчётов для внешнего перевозчика.           Структура готова к использованию в веб-приложении на      Laravel     . Для переноса в код миграций достаточно скопировать приведённые выше SQL-определения в методы       up     (     ) соответствующих миграций.
