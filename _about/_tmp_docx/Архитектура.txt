 
                Общее описание архитектурного стиля      Спроектированная архитектура системы представляет собой         модульный монолит     на базе фреймворка Laravel с         выделенным сервисом-адаптером     для интеграции с мессенджером Telegram. Выбор такого подхода обусловлен необходимостью централизованного управления бизнес-логикой и данными при одновременной поддержке двух клиентских каналов, имеющих различную природу взаимодействия (синхронный веб-интерфейс и асинхронный чат-бот).      Система разделена на три логических слоя:                Клиентские приложения     — веб-интерфейс и Telegram-бот, доступные как сотрудникам, так и руководителям.                Серверная часть (Backend)     — ядро системы на Laravel, содержащее маршрутизатор, модули бизнес-логики и обработчик очередей.                Данные и внешние системы     — хранилища MySQL и Redis, а также внешние API (Telegram, Яндекс.Карт) и результирующий Excel-файл.      Все компоненты взаимодействуют через чётко определённые интерфейсы: синхронные вызовы (HTTP, ORM) и асинхронные очереди (Redis). Такой подход обеспечивает         слабую связанность     клиентов и сервера,         отказоустойчивость     (выход из строя бота не влияет на веб-панель) и         масштабируемость     (возможность горизонтального расширения за счёт выноса ресурсоёмких операций в очереди).                        🧱         Детальное описание компонентов                1. Серверный слой (Backend)      Включает         ядро системы на Laravel Framework     и отдельный         сервис Telegram-бота    . Redis Queue                   Очередь сообщений для асинхронной обработки задач.                   Используется для выноса длительных операций (геокодирование) и рассылки уведомлений. Работает по принципу FIFO.                         Telegram Bot API                   Внешний облачный сервис, обеспечивающий взаимодействие с мессенджером Telegram.                   Предоставляет методы для получения обновлений и отправки сообщений.                         API Яндекс.Карт (Геокодер)                   Внешний сервис нормализации и валидации почтовых адресов.                   Принимает текстовую строку, возвращает структурированный адрес и координаты.                          Excel-файл для Яндекс Go                   Финальный артефакт работы системы.                   Файл в формате .xlsx или .csv, содержащий список одобренных заявок, готовый для загрузки в корпоративный кабинет Яндекс.Такси.                           🔄         Сценарии движения данных (потоки взаимодействия)                Сценарий 1: Подача заявки сотрудником через Telegram-бота                Сотрудник     отправляет команду /order в         Telegram Bot    .                Telegram Bot Service (Python)     проводит диалог с пользователем, запрашивая адрес, время, телефон. Выполняет первичную валидацию (формат времени, наличие обязательных полей).            После сбора всех данных         Telegram Bot Service     формирует JSON-объект и отправляет HTTP POST-запрос на эндпоинт         Маршрутизатора     ядра Laravel (POST /api/orders). В заголовках передаётся идентификатор пользователя Telegram.                Маршрутизатор     направляет запрос в цепочку middleware:            auth:api проверяет наличие и валидность токена (или Telegram ID).            can:create-order через         Модуль аутентификации и RBAC     убеждается, что пользователь имеет право создавать заявки.            После успешной авторизации запрос попадает в контроллер, который делегирует выполнение         Сервису управления заявками    .                Сервис управления заявками     создаёт новую запись в таблице temp_requests (буфер) со статусом pending.         Важно:     все поля сохраняются «как есть», адрес пока не нормализован.                Сервис управления заявками     формирует задание (Job) NormalizeAddressJob и отправляет его в         Redis Queue     (операция dispatch). Это асинхронный вызов — сервис не ждёт выполнения геокодера.                Сервис управления заявками     возвращает ответ 201 Created обратно по цепочке →         Маршрутизатор     →         Telegram Bot Service    .                Telegram Bot Service     отправляет сотруднику подтверждение:         «Заявка принята, ожидайте подтверждения руководителем»    .                 Параллельно в фоне:             Обработчик очередей (Worker)     забирает задание из         Redis Queue    , вызывает         API Яндекс.Карт     с исходным адресом, получает нормализованный адрес и обновляет соответствующую запись в temp_requests (поле address_norm).                Сценарий 2: Обработка заявок руководителем через веб-интерфейс                Руководитель     открывает веб-панель, где         Сервис управления заявками     через         Маршрутизатор     отображает список заявок из буфера (SELECT ... FROM temp_requests WHERE status = 'pending').            Для каждой заявки руководитель может выполнить действия:                Одобрить    :         Сервис управления заявками     обновляет статус записи в temp_requests на approved.                Отклонить    :         Сервис управления заявками     обновляет статус на rejected и сохраняет причину отказа.            При изменении статуса         Сервис управления заявками     генерирует событие (или напрямую вызывает         Сервис уведомлений    ).                Сервис уведомлений     формирует текст сообщения и через         Telegram Bot API     отправляет уведомление сотруднику:         «Ваша заявка одобрена»     или         «Заявка отклонена. Причина: ...»    .            В конце рабочего дня (или по требованию) руководитель нажимает кнопку         «Сформировать итоговый список»    .                Сервис управления заявками     в рамках         транзакции     выполняет:            INSERT INTO requests SELECT ... FROM temp_requests WHERE status = 'approved' AND date = TODAY            DELETE FROM temp_requests WHERE status = 'approved' AND date = TODAY            Таким образом, одобренные заявки перемещаются в основную таблицу requests, а буфер очищается.                Сценарий 3: Формирование и скачивание Excel-файла                Руководитель     в веб-интерфейсе нажимает кнопку         «Экспорт в Excel»    .            Запрос через         Маршрутизатор     и         Модуль аутентификации     поступает в         Сервис генерации отчетов    .                Сервис генерации отчетов     запрашивает у         Сервиса управления заявками     список всех одобренных заявок за текущий рабочий день (из таблицы requests).             Получив коллекцию данных,         Сервис генерации отчетов     с помощью библиотеки PhpSpreadsheet создаёт файл в формате, требуемом партнёром-перевозчиком.            Файл сохраняется во временное хранилище, и пользователю отдаётся HTTP-ответ с содержимым файла и заголовками Content-Disposition: attachment.            Руководитель скачивает файл и вручную загружает его в корпоративный кабинет         Яндекс Go     (действие за пределами разрабатываемой системы).                Сценарий 4: Просмотр истории заявок сотрудником                Сотрудник     (через веб или бота) запрашивает список своих заявок.            Запрос авторизуется, и         Сервис управления заявками     выполняет запрос к таблице requests с фильтром по user_id.            Результат возвращается клиенту и отображается в удобном виде (таблица в вебе, список сообщений в боте).                        🔗         Пояснения к ключевым связям (стрелкам)                                         Связь                      Тип                      Пояснение                         Веб-интерфейс → Маршрутизатор                   Синхронная (HTTP)                   Классические запросы браузера к серверу (GET/POST). Используется сессионная аутентификация.                         Telegram Bot Service → Маршрутизатор                   Синхронная (REST API JSON)                   Бот отправляет структурированные данные на специальные API-эндпоинты Laravel. Аутентификация по Telegram ID или токену.                         Маршрутизатор → Модуль аутентификации                   Внутренний вызов                   Передача запроса через middleware-посредники для проверки прав.                         Модуль аутентификации → Сервис заявок                   Внутренний вызов                   После успешной авторизации управление передаётся соответствующему сервису.                          Сервис заявок → Буфер (temp_requests)                   Синхронная (Eloquent ORM)                   Все новые заявки немедленно сохраняются в буферную таблицу.                         Сервис заявок → MySQL Database                   Синхронная (CRUD-операции)                   Чтение/обновление/удаление записей в таблицах requests и temp_requests.                         Сервис заявок → Redis Queue                   Асинхронная (dispatch)                   Постановка фоновых задач (геокодирование) без ожидания результата.                         Обработчик очередей → API Яндекс.Карт                   Синхронная (HTTP)                   Worker выполняет длительный внешний вызов, не блокируя основной веб-поток.                         Сервис заявок → Сервис уведомлений                   Асинхронная (событие/вызов)                   При изменении статуса заявки инициируется отправка уведомления.                         Сервис уведомлений → Telegram Bot API                   Синхронная (HTTP)                   Отправка сообщения конкретному пользователю через API Telegram.                         Сервис отчётов → Сервис заявок                   Внутренний вызов                   Получение данных, необходимых для генерации Excel.                         Сервис отчётов → Excel-файл                   Генерация файла                   Создание и сохранение файла на диске / в памяти с последующей отдачей.                               Telegram Bot Service → Telegram Bot API                   Синхронная (HTTP)                   Получение обновлений (сообщений от пользователей) и отправка ответов в мессенджер.                              Буфер          (temp_requests) → MySQL Database                   Логическая связь                   Указывает, что буфер физически является частью базы данных MySQL (хранится в ней).                            📝         Итоговое резюме по архитектуре      Спроектированная архитектура полностью отвечает требованиям, сформулированным в главе 1:                Равноправный доступ     сотрудников и руководителей к веб-интерфейсу и Telegram-боту.                Централизованное управление     бизнес-логикой и данными через ядро Laravel.                Двухэтапная обработка заявок     с использованием буферной таблицы для контроля качества.                Асинхронное выполнение     ресурсоёмких операций (геокодирование) через очереди Redis, обеспечивающее высокую отзывчивость интерфейса.                Модульность     и слабая связанность компонентов, что упрощает тестирование, сопровождение и масштабирование системы.
